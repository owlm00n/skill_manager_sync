## 根因分析

### 根本原因

**未读取官方 CTS 规范 PDF。** 所有内容均来自次级信息源：

```
信息源                         →  推理过程              →  错误产物
─────────────────────────────────────────────────────────────────────
Bug 3397942 Fail 描述          →  推断测试目的           →  错误名称
Bug 仪表报告 (Run #1, #2, #3)  →  推断测试结构           →  虚构子测试
已有 CTS 模板 (多 PDO 切换)    →  推断 PDO 场景          →  虚构多 PDO
PD 协议通用知识                →  推断协商流程           →  虚构步骤
Bug 讨论中的观测数据           →  推断检查点             →  虚构判定标准
```

### 为什么推断不可靠

1. **CTS 测试的设计意图不可推断**: SNK.14 的核心设计（1ms 等待 + 50 次重试）是测试设计者的刻意选择，无法从 Bug 现象逆向推导
2. **测试条件 ≠ 测试步骤**: 仪表报告中的 Rev2Snk/Rev3ChkdSnk 是测试条件标记，不是步骤
3. **单 PDO 是刻意选择**: 规范选择单 PDO 是为了简化测试、聚焦 GoodCRC 时序问题
4. **观测数据 ≠ 判定标准**: Bug 讨论中的 "GoodCRC 2ms" 是调试数据，不是规范要求

## 正确流程

### 生成 CTS 流程文件的强制步骤

```
步骤 1: 读取 CTS 规范 PDF 对应章节 → 提取规范原文
步骤 2: 按模板格式填充规范内容（名称、目的、步骤、检查点）
步骤 3: 搜索 Bug 数据库 → 补充失败模式和参考案例（标记来源）
步骤 4: 在文件末尾标注来源（PDF 页码 + Bug ID）
```

### 禁止事项

| 禁止 | 原因 |
|------|------|
| ❌ 从 Bug Fail 描述推断测试名称/目的 | Fail 现象 ≠ 测试的 Pass 标准 |
| ❌ 从仪表报告格式推断测试步骤 | 报告格式 ≠ 测试步骤 |
| ❌ 从已有 CTS 文件推断测试内容 | 格式模板 ≠ 内容模板 |
| ❌ 将 PD 协议通用知识当作 CTS 设计 | 通用协议 ≠ 特定测试设计 |

### 内容边界

| 内容类型 | 来源 | 标注方式 |
|---------|------|---------|
| 测试名称/目的/步骤/检查点 | 官方 CTS 规范 PDF | 不加标记 |
| 常见失败模式 | Bug 根因分析 | 标注 "→ 通常原因:" |
| 参考 Bug 案例 | Bug 管理系统 | 标注 Bug ID |
| 调试方法 | 项目实践经验 | 标注 "→ 调试方法:" |
