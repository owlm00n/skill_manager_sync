🎯 根因结论

CC 检测功能在 PR_Swap 期间被提前禁用，导致 sprd_tcpm 状态机在 PR_SWAP_SNK_SRC_SINK_OFF 状态下无法完成向 Source 角色的转换。

故障机制

sc27xx_typec_pr_swap_no_chk_detach(on=1) 在 PR_Swap 消息到达前就被 CC 检测中断 (irq=78) 触发，提前禁用了 SC27xx PMIC 的 CC 检测功能。sprd_tcpm 状态机进入 PR_SWAP_SNK_SRC_SINK_OFF 后，需要 CC 线状态变化事件来触发向 PE_PRS_SNK_SRC_Assert_Rp 的转换，但由于 CC 检测被禁用，该事件永远不会产生，状态机在 835ms (tPSSourceOffTimer) 后超时进入 ERROR_RECOVERY。

核心问题

  1. 时序竞争: CC 中断 (irq=78) 在 PR_Swap 消息到达前 30ms 触发，导致 CC 检测被提前禁用
  2. 功能过度禁用: pr_swap_no_chk_detach(on=1) 不仅阻止了断开检测，还阻止了正常的状态变化事件
  3. 状态机阻塞: sprd_tcpm 在 PR_SWAP_SNK_SRC_SINK_OFF 状态等待的转换条件永远无法满足

为什么 PD 2.0 通过但 PD 3.0 失败？

PD 3.0 测试模式下，Tester 在发送 PR_Swap 前的 CC 线操作触发了 SC27xx PMIC 的 CC 检测中断 (irq=78)，导致 pr_swap_no_chk_detach 被提前调用。PD 2.0 测试模式下无此行为，CC 检测保持正常，状态机可正常完成 PR_Swap 转换。

🔧 修复建议

修复方向 1 (推荐): 调整 pr_swap_no_chk_detach 调用时机

目标: 确保 CC 检测仅在 PR_Swap 消息确认后才禁用，而非在 CC 中断中提前禁用。

将 sc27xx_typec_pr_swap_no_chk_detach(on=1) 的调用从 CC 中断处理函数中移除，改为在 sprd_tcpm 状态机确认进入 PR_SWAP_ACCEPT 后再调用。

修改前:
  CC irq (irq=78) → pr_swap_no_chk_detach(on=1)  // 过早禁用

修改后:
  PR_Swap 消息到达 → PR_SWAP_ACCEPT → pr_swap_no_chk_detach(on=1)

修复方向 2: 分离 CC 断开检测和状态变化事件

目标: 确保 PR_Swap 期间只禁用断开检测，CC 状态变化事件保持正常。

在 sc27xx_typec_pr_swap_no_chk_detach() 内部，将 CC 断开检测和 CC 状态变化事件分离为两个独立的控制路径，仅禁用断开检测，保持状态变化事件启用。

修复方向 3: 主动 CC 角色切换

目标: 不依赖 CC 检测事件，主动命令 SC27xx PMIC 切换 CC 角色。

在进入 PR_SWAP_SNK_SRC_SINK_OFF 后，主动向 SC27xx PMIC 发送 CC 角色切换命令（Rd→Rp），使用轮询或直接回调方式确认切换完成，而非依赖被动的 CC 检测事件。

  2. 验证 Reg2Snk 仍通过 — 确保 PD 2.0 PR_Swap 不受影响
  3. 检查 kernel log — 确认 pr_swap_no_chk_detach 调用时机正确，CC 状态变化事件正常产生
  4. 检查 CC 线切换日志 — 确认 PR_SWAP_SNK_SRC_SINK_OFF 后有 CC 线 Rd→Rp 切换日志
