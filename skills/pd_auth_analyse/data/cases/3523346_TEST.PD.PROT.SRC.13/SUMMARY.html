🎯 根因结论

SC27XX PD Controller PHY 层在 PR_Swap Rd transition 后，BMC 发送电路恢复延迟导致 PS_RDY 消息发送时 CRCReceiveTimer 重试耗尽（int sts=0x40），驱动 cleanup 路径 + HW 内部重试 + 固件 PHY 初始化等待的总时间在 Aug 21 固件版本上超过 tCtsErrorRecovery 15ms 限值约 1ms，导致认证失败。

关键证据链：

  1. int sts=0x40 (TX error) 在 所有三份 log 中均出现（包括 PASS 的 Aug 24/27），证明 TX 错误不是 Bug 本身，而是 SC27XX 硬件的已知行为特征。
  2. 驱动 cleanup 路径 ERROR_RECOVERY → PORT_RESET 在三份 log 中完全一致（~2.6-2.8ms），证明修复不在 kernel 驱动层。
  3. HW 内部 CRCReceiveTimer 重试约 ~3ms + 驱动 cleanup ~2.6ms = ~5.6ms 固定开销。剩余 ~10ms 来自 SC27XX 固件的 PHY 初始化等待，这是 Aug 21→Aug 24 修复的关键变量。
  4. 同平台 Bug 3523357 (SRC3.01) 已确认 SC27XX 存在硬件自动行为（enable_tx_auto_retry）干扰 PD 协议时序，进一步佐证固件层修复路径。

🔧 修复建议

Rev2Src SRC.13#3 （主问题）

优先级方案
P0 更新 SC27XX PD Controller 固件 到 Aug 24/27 已验证的版本。修复已在固件中存在，不需要 kernel 代码修改。
P0 获取 SC27XX 固件 changelog，确认 Aug 21→Aug 24 的具体变更（BMC PHY 初始化时序优化 / CC debounce 减少 / CRCReceiveTimer 配置变更）。
P1 评估禁用 enable_tx_auto_retry（参考 Bug 3523357 修复）：可减少 HW 内部重试时间，缩短 tCtsErrorRecovery 总量，但不会消除 TX 错误本身。

Rev3ChkdSrc BU.1#1 （子问题）

优先级方案
P1 检查 PD 3.0 VIF 配置：当前 VIF 可能仅配置 PD 2.0 Source-only 模式，不支持 PD 3.0 Sink。
P1 检查 bq2560x OTG enable 逻辑：PD 3.0 Sink 模式下 VBus 源切换可能失败。在 Aug 27 log 中搜索 bq2560x.*OTG 确认。
P2 确认 charger IC 配置：sgm41542s/sgm41516S 在 PD 3.0 模式下的寄存器设置。

✅ 复测验证

  1. 固件更新验证：确认 SC27XX PD Controller 固件与 Aug 24/27 PASS 版本一致
  2. Rev2Src SRC.13 复测：PR_Swap Source→Sink 后 tCtsErrorRecovery ≤ 15ms
  3. Rev3ChkdSrc BU.1 复测：PD 3.0 Sink 模式下 VBus 正常建立，无 0x000003A9 错误
  4. 多次循环测试：同一 session 中的额外 PR_Swap 子测试也需通过（防止 Aug 27 Session 1 首次失败的重现）
  5. kernel log 交叉验证：确认 int sts=0x40 存在但不再导致 tCtsErrorRecovery 超限
