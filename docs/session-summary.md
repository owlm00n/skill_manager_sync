## 三、为什么交互这么多轮

### 3.1 根本原因分析

**1. 需求不明确，边做边改**
- 用户初始需求模糊："修改一个管理方式"
- 没有完整的需求文档或原型
- 功能逻辑参考 skills-manager 但用户自己也在学习
- 导致：做了→不对→改→还不对→再改 的循环

**2. 缺乏系统性测试**
- 助手没有在每个功能完成后进行端到端测试
- 用户承担了测试角色，发现大量基础问题
- 导致：批量报 Bug → 批量修复 → 又发现新问题

**3. 前端代码质量问题**
- 全局状态 (`SYNC_STATUS`) 管理混乱
- `refresh()` 函数调用链不清晰（同步/异步混用）
- 渲染函数不 await 异步操作
- 导致：改一处动全身，修不好

**4. 过度依赖用户验证**
- 助手声称"后端正常"但没有写自动化测试
- 前端问题靠用户 Console 日志定位
- 导致：反复"你试试"→"不行"→"再试试"

**5. 上下文溢出导致重复工作**
- 3 次上下文溢出，每次丢失之前的工作状态
- 新上下文需要重新理解代码、重新定位问题
- 导致：同一个 Bug 跨会话反复调试

## 四、如何避免多轮低效交互

### 4.1 事前规划（最重要）

| 做法 | 效果 |
|------|------|
| **先写完整需求文档再动手** | 避免"做了→不对→重做"循环 |
| **先出 Plan 让用户确认** | 对齐预期，减少返工 |
| **明确功能边界和验收标准** | 避免无限追加功能 |

**本次教训**：没有需求文档，用户边想边说，助手边做边改。46 条用户消息中有 30+ 条是"这不对"、"还有问题"、"还是不行"。

### 4.2 开发流程

| 做法 | 效果 |
|------|------|
| **每完成一个功能立即端到端测试** | 及早发现问题 |
| **前端修改后在浏览器中验证** | 不要只测后端 API |
| **修改前先理解完整数据流** | 不要头痛医头 |

**本次教训**：助手多次声称"API 正常"但没有验证前端。如果第一次修改后就在浏览器中测试，不会拖 8 轮。

### 4.3 调试策略

| 做法 | 效果 |
|------|------|
| **前端 Bug 先加最小复现** | 不要猜，直接看 |
| **二分法缩小问题范围** | 先确认数据在哪一步变错 |
| **不要同时改多个东西** | 一次只改一个变量 |

**本次教训**：Preset Bug 调试了 8 轮，助手反复修改不同文件（workspace.js、app.js、web-ui.py），没有系统性地二分定位问题。

### 4.4 上下文管理

| 做法 | 效果 |
|------|------|
| **大任务拆分为独立子任务** | 避免上下文溢出 |
| **每个子任务完成后生成总结** | 续接时快速恢复 |
| **关键决策写入 Memory** | 跨会话保持一致 |

**本次教训**：3 次上下文溢出，每次续接都浪费 5-10 轮重新理解代码。

## 五、经验总结

### 5.1 技术经验

1. **Windows Junction 删除**：`shutil.rmtree()` 无法删除 Junction（reparse point），必须用 `os.rmdir()`
2. **PowerShell YAML 解析**：自定义解析器必须显式处理空数组 `[]`、空字符串等边界情况
3. **前端全局状态**：`refresh()` 类函数必须 await 所有异步渲染，否则状态不一致
4. **Windows 路径转义**：HTML `onclick` 中的路径需要双重转义反斜杠

### 5.2 流程经验

1. **先测后端，再测前端**：确认 API 正常后再查前端
2. **一次只改一个变量**：不要同时改前端和后端
3. **用浏览器 DevTools 调试**：不要靠猜，直接看 Network 和 Console
4. **写自动化测试**：关键 API 应该有测试脚本，不要靠手动验证

### 5.3 沟通经验

1. **先理解再动手**：用户说"preset 不工作"时，先确认他期望的行为是什么
2. **不要过度承诺**：说"已修复"之前一定要验证
3. **主动提供选项**：当有多种方案时，列出优劣让用户选
4. **识别"死胡同"**：如果同一个问题修了 3 次还不行，换个思路

### 5.4 如果重来一次

理想的会话流程应该是：

```
1. 需求文档（1-2 轮）
   → 确认功能范围、参考 skills-manager、确定技术栈

2. 架构设计 + Plan（2-3 轮）
   → 文件结构、API 设计、数据流、用户确认

3. 分模块实现（每模块 3-5 轮）
   → Library → Sync → Global WS → Project WS → Preset
   → 每个模块完成后端到端测试

4. 集成测试（3-5 轮）
   → 全流程测试、修 Bug

总计：~25-35 轮（实际 46 轮，且核心 Bug 未解决）
```
